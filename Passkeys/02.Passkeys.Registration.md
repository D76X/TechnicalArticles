# Microsoft Entra Passkey Registration Campaigns: Design, Configuration, and Rollout

Enabling passkeys in Microsoft Entra ID does not make users register them. The authentication-method policy defines what is permitted, but adoption still depends on users finding the Security info page, understanding the available choices, and completing registration successfully.

A **passkey registration campaign** closes that gap. After an in-scope user completes normal sign-in and multifactor authentication (MFA), Entra can interrupt the flow with a prompt to create a passkey. Administrators can control campaign state, target population, snooze behavior, and whether registration becomes mandatory after repeated postponement.

John Savill's *Entra Passkey Registration Campaign* video [1] explains both the feature and its most important operational subtlety: the nudge is evaluated in the context of the current device and browser, while passkey-profile restrictions determine what the user is actually allowed to create. This article develops that explanation into an implementation guide based on Microsoft Learn documentation updated in May 2026 [2]. Because this feature is actively evolving, validate all production settings against current documentation before rollout.

## 1. What problem the campaign solves

Passkeys are useful only after registration. An organization can publish instructions, but voluntary migration is often slow. Users have little incentive to replace a familiar method until the stronger method appears directly in their normal workflow.

The campaign provides a managed nudge at the right point in that workflow:

1. The user signs in normally.
2. The user completes Microsoft Entra MFA.
3. Entra evaluates campaign scope and eligibility.
4. If the user needs an applicable local passkey, Entra prompts for registration.
5. The user registers, postpones the prompt, or handles an error and continues according to policy.

The campaign does not itself authenticate the user and does not silently create a credential. It starts an interactive registration ceremony after the user has already performed MFA.

Microsoft Entra registration campaigns can target one of two methods [2]:

- **Passkey (FIDO2):** synced or device-bound passkeys, subject to the user's assigned passkey profiles.
- **Microsoft Authenticator:** Authenticator configured for push notifications.

A tenant can target **only one method at a time**. It cannot run an Authenticator campaign and a passkey campaign concurrently, even for different groups. This constraint must be considered when planning a staged migration.

## 2. Why passkeys are worth promoting

A passkey uses a unique public/private key pair for a relying party. The service stores the public key; the authenticator or credential provider protects the private key. During sign-in, the private key signs a fresh challenge after local user interaction. The private key is not transmitted to Entra [4][10][11].

This gives the campaign a stronger security objective than simply increasing MFA registration:

- there is no reusable password or one-time code to phish;
- the credential is cryptographically scoped to the genuine relying party;
- a stolen public-key database does not enable account impersonation;
- cross-device use requires an intentional ceremony and nearby authenticator;
- a local biometric or PIN can verify the user without becoming a network credential.

The campaign should still be described accurately to users. Passkeys reduce credential phishing and credential stuffing; they do not prevent malware, stolen sessions, insecure recovery, malicious consent, or use of an already unlocked device.

## 3. Understand the three policy layers

A reliable deployment separates three controls that are easy to confuse.

### 3.1 Authentication-method policy: may the user use a passkey?

The **Passkey (FIDO2)** authentication-method policy enables the method for selected users and groups. Its configuration includes **Allow self-service setup**, which must be enabled for a passkey campaign [2][3].

If the user is not enabled for passkeys, or self-service setup is disabled, a campaign cannot produce a successful self-service registration.

### 3.2 Passkey profiles: what kind of passkey may the user register?

Passkey profiles constrain credentials for assigned groups [3][7]. Depending on current product capabilities, a profile can specify:

- whether device-bound credentials are allowed;
- whether synced credentials are allowed;
- whether authenticator attestation is required;
- whether registration is limited to specified Authenticator Attestation GUIDs (AAGUIDs).

Profiles let an organization create assurance tiers. General employees might be allowed synced or device-bound passkeys for usability, while privileged administrators might be limited to evaluated, device-bound authenticators. A restriction is useful only when the organization can support its registration and recovery consequences.

### 3.3 Registration campaign: should Entra prompt now?

The campaign decides who receives a nudge, what method is promoted, and how postponement works. It does not override the authentication-method policy or passkey profile. If the campaign invites a user to create a credential that their profile rejects, registration fails.

### 3.4 Conditional Access: where is the method required?

Registration is not enforcement. A user can possess a passkey while continuing to use another allowed sign-in method. Conditional Access authentication strengths can require **phishing-resistant MFA** for selected resources or populations [5].

A sensible sequence is therefore:

1. permit the correct passkey types;
2. register users;
3. confirm successful use and recovery readiness;
4. enforce phishing-resistant authentication where required;
5. retire weaker methods when operationally safe.

## 4. Prerequisites

Microsoft documents the following core prerequisites for passkey campaigns [2]:

- Microsoft Entra MFA must be enabled and used; the nudge does not work with a non-Entra MFA service.
- The Passkey (FIDO2) method must be enabled in the authentication-method policy for the intended users.
- **Allow self-service setup** must be enabled.
- An administrator configuring the campaign needs at least the **Authentication Policy Administrator** role.
- Conditions governing security-information registration must allow the operation.

There is no separate license requirement for the registration campaign itself, according to the current documentation [2]. Other controls used in the rollout, such as particular Conditional Access features, can have their own licensing requirements.

Before enabling the campaign, also verify:

- supported operating-system and browser combinations;
- passkey profiles assigned to each target group;
- mobile-device management and compliance requirements;
- availability of Temporary Access Pass for bootstrap or recovery;
- help-desk identity-proofing and lost-device procedures;
- emergency-access exclusions;
- the current registration baseline from Authentication methods activity reports.

## 5. Campaign state and Microsoft-managed behavior

The campaign has three states.

### Disabled

No registration-campaign nudge is generated. Users can still register methods through other supported paths if policy permits.

### Enabled

The administrator explicitly configures the target method and campaign behavior. For a passkey campaign, select **Passkey**. Current settings include the tenant-wide snooze duration, whether the number of snoozes is limited, and include/exclude targeting [2].

This mode provides control, but it also makes the administrator responsible for aligning the selected population with passkey-profile restrictions.

### Microsoft managed

Microsoft selects recommended campaign defaults and rolls changes out incrementally. As documented in May 2026, Microsoft-managed tenants are moving toward [2]:

- targeting passkeys rather than Authenticator;
- a one-day snooze duration;
- unlimited snoozes;
- targeting all MFA-capable users rather than only voice-call or text-message users.

These values are service-managed and are not configurable while this state is selected. Include/exclude targets remain configurable.

There is an important safeguard: if the tenant targets specific AAGUIDs in the Passkey (FIDO2) policy, the Microsoft-managed campaign does not switch its target to passkeys. More generally, the Microsoft-managed passkey nudge is suppressed for a user whose passkey profile is restricted to synced-only, device-bound-only, enforced attestation, or AAGUID restrictions [2].

This behavior differs from a manually enabled campaign. Administrators can explicitly enable and target passkeys, but must then prevent restricted users from being led into an incompatible registration path.

## 6. Snooze and enforcement semantics

When the campaign is explicitly enabled, **Days allowed to snooze** can be set from 0 through 14 days [2]. A value of 0 means the user can be prompted at every MFA attempt. A nonzero value defines the delay before the next interrupt prompt after the user selects **Skip for now**.

**Limited number of snoozes** controls whether postponement eventually ends:

- **Disabled:** the user can keep postponing indefinitely.
- **Enabled:** the user can skip three times; subsequent eligible sign-in requires registration.

The snooze count is tracked per user and persists across campaign restarts and configuration changes, including a change in the targeted method [2]. This has migration consequences. Switching a mature Authenticator campaign to passkeys does not necessarily give every user three new postponements.

Closing the browser counts as snoozing. By contrast, a skip offered after a registration error does **not** consume a limited snooze. This prevents a technical failure from blocking sign-in after the allowance is exhausted.

The snooze duration is tenant-wide. Different groups cannot have different delays in the same tenant. Population staging therefore uses targeting and exclusions rather than per-group snooze settings.

## 7. How Entra decides whether to show the passkey nudge

The passkey evaluation is not a simple account-level question such as “Does this user have any passkey?” It asks whether the user has a passkey applicable to the **current device and browser combination** [2].

This explains behavior that otherwise looks inconsistent:

- A Windows Hello for Business credential suppresses the nudge on Windows, but not when the same user signs in on a Mac.
- A Google Password Manager passkey can suppress it on Android and supported Chrome combinations, but not every browser on Windows or macOS.
- An iCloud Keychain passkey can suppress it across supported Apple experiences and Chrome on macOS.
- A Microsoft Authenticator passkey suppresses it on supported iOS and Android experiences.
- A nonplatform provider such as a roaming security key or supported authenticator app can satisfy the evaluation across more combinations.

The current Microsoft platform matrix is summarized below [2]. A dash means that credential does not suppress the nudge in that combination.

| Credential visible to the experience | Windows + Chrome | Windows + other | Mac + Chrome | Mac + other | iOS | Android |
|---|---:|---:|---:|---:|---:|---:|
| Windows Hello for Business | Yes | Yes | — | — | — | — |
| Microsoft Entra passkey on Windows | Yes | Yes | — | — | — | — |
| Google Password Manager | Yes | — | Yes | — | — | Yes |
| iCloud Keychain, including managed | — | — | Yes | Yes | Yes | — |
| Mac Platform SSO | — | — | Yes | Yes | — | — |
| Samsung Pass | — | — | — | — | — | Yes |
| Passkey in Microsoft Authenticator | — | — | — | — | Yes | Yes |
| Nonplatform provider, including security keys | Yes | Yes | Yes | Yes | Yes | Yes |

The matrix is product behavior, not a timeless property of WebAuthn. Use the live Microsoft Learn table when designing or troubleshooting a campaign.

### Operational implication

A user can be prompted several times on different devices or browsers. This is not necessarily duplicate account-level registration logic. Entra is trying to ensure that an applicable credential is available in each context the user actually uses.

This also means that a user who created a device-bound passkey on one phone can still be prompted on another device. A synced credential may reduce repeated prompts in combinations where the credential provider exposes it, but synchronization support and visibility are provider- and platform-specific.

## 8. The profile-restriction trap

The video's most valuable warning is the gap between **nudge eligibility** and **registration-policy compatibility** [1]. Consider this example:

1. A privileged-user profile permits only device-bound passkeys.
2. An administrator manually enables a passkey campaign for all users.
3. A targeted user is prompted on an iPhone.
4. The default or most obvious choice is a synced iCloud Keychain credential.
5. Registration reaches Entra, but the assigned profile rejects the synced credential.

The campaign has not weakened policy—the disallowed credential is still rejected—but it has created a confusing user experience and a support incident.

Use one or more of these mitigations:

- keep Microsoft-managed behavior for populations with restrictions, accepting that restricted profiles are not nudged;
- explicitly target only groups whose profiles allow the natural registration choices on their devices;
- run separate waves for each profile type;
- give exact, illustrated instructions telling restricted users which credential provider or security key to select;
- validate every profile/device/browser path in a pilot before making registration mandatory;
- provide a direct support route and ensure registration-error skips remain available.

Do not weaken authenticator requirements merely to make a campaign succeed. Align campaign scope and guidance to the intended assurance policy.

## 9. Configure the campaign in the Entra admin center

Using the current portal experience [2]:

1. Sign in to the [Microsoft Entra admin center](https://entra.microsoft.com) as an Authentication Policy Administrator or a more privileged appropriate role.
2. Go to **Entra ID** > **Authentication methods** > **Policies**.
3. Open **Passkey (FIDO2)** and confirm that the pilot population is enabled, assigned the intended profiles, and allowed self-service setup.
4. Return to **Authentication methods** > **Registration campaign** and select **Edit**.
5. Choose **Microsoft managed**, **Enabled**, or **Disabled**.
6. If **Enabled** is selected, choose **Passkey** as the authentication method.
7. Configure the snooze duration and whether snoozes are limited.
8. Configure include/exclude targets available in the portal. Exclusions take precedence when a user is both included and excluded.
9. Save the policy.
10. Test with accounts representing every relevant passkey profile and client platform.

Avoid changing campaign targeting and Conditional Access enforcement simultaneously. If users cannot sign in, it should be clear whether the problem is registration, authenticator compatibility, recovery, or access policy.

## 10. Configure the campaign with Microsoft Graph

Automation uses the authentication-methods policy endpoint [8]. Microsoft documents these delegated permissions for Graph Explorer [2]:

- `Policy.Read.All`
- `Policy.ReadWrite.AuthenticationMethod`

First retrieve the current policy:

```http
GET https://graph.microsoft.com/v1.0/policies/authenticationMethodsPolicy
```

Then patch only the `registrationEnforcement` section that must change:

```http
PATCH https://graph.microsoft.com/v1.0/policies/authenticationMethodsPolicy
Content-Type: application/json
```

The following example targets all users for passkey registration, allows a one-day snooze, and requires registration after three snoozes:

```json
{
  "registrationEnforcement": {
    "authenticationMethodsRegistrationCampaign": {
      "snoozeDurationInDays": 1,
      "enforceRegistrationAfterAllowedSnoozes": true,
      "state": "enabled",
      "excludeTargets": [],
      "includeTargets": [
        {
          "id": "all_users",
          "targetType": "group",
          "targetedAuthenticationMethod": "fido2"
        }
      ]
    }
  }
}
```

For a pilot, replace `all_users` with the object ID of the pilot group. A target can be a `user` or `group`; the ID is the corresponding Entra object ID. Use `targetedAuthenticationMethod: "fido2"` for passkeys and `"microsoftAuthenticator"` for an Authenticator campaign.

Before patching production:

- export the existing policy response;
- preserve unrelated properties;
- use least-privilege administrative roles and Graph permissions;
- test the JSON against a nonproduction tenant where possible;
- confirm the resulting effective portal state;
- record the change through normal identity-governance controls.

## 11. Interaction with Conditional Access

Conditional Access policies governing the **Register security information** user action apply before the nudge [2]. If registration is allowed only from a trusted location or compliant device, users outside those conditions are not prompted. A policy that blocks the registration page also suppresses the nudge.

Other documented suppression cases include:

- the user is already signed in through SSO, so no qualifying sign-in interruption occurs;
- a Terms of Use screen appears in the sign-in flow;
- a Conditional Access custom control redirects the user;
- the experience is an unsupported out-of-box or embedded-browser flow.

After enrollment, Conditional Access can require a phishing-resistant authentication strength. It can also independently require a compliant or managed device. These controls are complementary: a synced passkey can provide strong, RP-bound authentication, while device-compliance policy limits which endpoints may access corporate resources.

## 12. Platform and population limitations

As of the May 2026 Microsoft Learn guidance [2]:

- Linux users are not nudged because Entra FIDO2 passkeys are not available in that documented campaign path.
- Passkey campaigns support browser-based mobile experiences and native iOS mobile apps; native Android application support is not yet available.
- Authenticator registration campaigns are not supported on mobile devices.
- Guest/B2B users can be nudged for an Authenticator campaign, but not a passkey campaign because passkey support for guest users is not available in this feature.
- A campaign can run indefinitely until an administrator disables it.
- Passwordless phone sign-in is not a campaign target.

These are service limitations and can change. They should be represented in the rollout's support matrix, not assumed from the FIDO standards themselves.

## 13. A safe rollout plan

### Phase 1: establish the baseline

Use the Authentication methods activity report to measure existing passkeys, Authenticator registrations, and the populations still dependent on weaker methods [9]. Inventory devices, browsers, privileged roles, shared-device scenarios, and users who require accessibility accommodations.

Define success in measurable terms, for example:

- percentage of target users with a usable passkey;
- percentage of interactive sign-ins using phishing-resistant methods;
- registration success and failure rates;
- help-desk contacts per enrollment wave;
- recovery time after device loss;
- reduction in SMS, voice, and password-plus-push use.

### Phase 2: design profiles and recovery

Assign passkey profiles based on risk rather than organizational convenience. Decide where synced passkeys are acceptable and where device-bound, attested, or AAGUID-restricted credentials are justified.

Then design the failure paths:

- lost, stolen, replaced, or wiped device;
- forgotten local authenticator PIN;
- user changes mobile ecosystem;
- authenticator model becomes vulnerable or unsupported;
- user has no compatible device;
- user is remote and cannot satisfy security-information registration conditions.

Temporary Access Pass can bootstrap a new passwordless method after appropriate identity verification [6]. High-risk users can also register multiple independent authenticators, such as a primary platform credential and a secured backup key.

### Phase 3: technical pilot

Select a small group that includes different operating systems, browsers, locations, and profile restrictions. Keep snoozes unlimited initially so a defect does not block work.

Test at least:

- same-device registration and sign-in;
- phone-to-computer cross-device sign-in;
- each synced credential provider allowed by policy;
- each approved device-bound authenticator;
- a deliberately disallowed authenticator;
- device replacement and recovery with TAP;
- several browsers on the same operating system;
- Conditional Access registration restrictions;
- campaign exclusion and emergency-access behavior.

### Phase 4: communication pilot

A passkey prompt is simple only when the user understands which option to choose. Communications should explain:

- why the organization is moving away from passwords and phishable MFA;
- whether users may choose synced passkeys, device-bound passkeys, or both;
- which phone, browser, or hardware-key options are supported;
- that a biometric remains local to the device;
- what the QR-code cross-device flow does;
- how to recognize the official registration prompt;
- where to get help and what happens after postponement.

For restricted profiles, instructions must name the permitted provider or authenticator. Generic advice to “create a passkey” is insufficient.

### Phase 5: broad registration

Expand by profile-compatible groups. Monitor failures and help-desk demand after every wave. Use explicit **Enabled** targeting when the organization needs predictable timing and behavior; use **Microsoft managed** when Microsoft-recommended defaults and automatic service evolution fit the risk model.

Only enable limited snoozes after registration paths are proven. Remember that snooze counts persist across policy changes.

### Phase 6: enforce and optimize

Once coverage and recovery are adequate, apply phishing-resistant authentication strengths to selected resources or populations. Start with high-value administrative portals and privileged roles, then expand according to business risk.

Continue measuring actual sign-in methods. Registration count alone can overstate progress if users retain and prefer weaker methods. Remove obsolete methods and fallback paths in controlled stages.

## 14. Troubleshooting logic

When a user does not receive a nudge, check in this order:

1. Did the user perform Microsoft Entra MFA in this sign-in?
2. Is the campaign enabled or Microsoft managed, and is passkey the effective target?
3. Is the user included and not excluded?
4. Is Passkey (FIDO2) enabled for the user with self-service setup allowed?
5. Under Microsoft-managed mode, does the user's profile contain a restriction that suppresses the nudge?
6. Does Entra detect an applicable local passkey for this device/browser combination?
7. Is the snooze interval still active?
8. Did SSO, Terms of Use, a custom control, or registration Conditional Access suppress the interruption?
9. Is this platform and application flow supported?

When a user receives the nudge but registration fails, shift attention to policy compatibility:

1. Which passkey provider or authenticator did the user select?
2. Is it synced or device-bound, and does the assigned profile allow that type?
3. Is attestation required and supported?
4. Is its AAGUID allowed?
5. Are the operating system, browser, and Authenticator versions supported?
6. Can the user access Security info under current Conditional Access conditions?

This separation—**why no nudge** versus **why registration failed**—usually shortens diagnosis.

## 15. Security and governance considerations

A campaign changes authentication-method enrollment at scale, so treat it as a security-sensitive deployment.

- Protect Authentication Policy Administrator assignments through least privilege and privileged identity management.
- Audit changes to authentication-method and campaign policies.
- Monitor unusual passkey registrations and deletions.
- Protect TAP issuance with strong help-desk verification and short lifetimes.
- Maintain emergency-access accounts outside policies that could lock out the tenant.
- Document approved credential providers and their synchronization/recovery trust models.
- Review AAGUID allowlists and attestation requirements as products evolve.
- Re-test campaign behavior after major operating-system, browser, or Entra changes.

A campaign should never become a substitute for identity proofing. It is safe because it follows a successfully authenticated session and remains subject to registration policy. Weak bootstrap or recovery can still undermine the stronger credential.

## Conclusion

The Entra passkey registration campaign is an adoption mechanism, not the passkey security mechanism itself. Its job is to place a well-timed enrollment prompt after MFA and move users toward a stronger, easier sign-in method.

Successful rollout depends on aligning four things: the authentication-method policy, assigned passkey profiles, campaign targeting, and Conditional Access. The current device-and-browser evaluation explains why the same user can be nudged in one context but not another. Profile restrictions explain why a nudge can appear even though the user's first credential choice is rejected in a manually enabled campaign.

The safest approach is linear: define acceptable credentials, prepare recovery, pilot every user journey, communicate the permitted choice, run targeted enrollment waves, and only then require phishing-resistant authentication. With that sequence, the campaign becomes a controlled migration tool rather than a source of failed registrations and help-desk calls.
