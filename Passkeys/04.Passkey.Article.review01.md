# What is reverse-proxy credential phishing?

Reverse-proxy credential phishing (also known as Adversary-in-the-Middle or AiTM phishing) is an advanced cyberattack 
where an attacker places a live server between a victim and a real login website to steal login details and bypass 
multi-factor authentication (MFA). [1, 2] 

------------------------------

## How the Attack Works
Unlike traditional phishing—which uses a static fake page that just copies what you type — a reverse-proxy attack acts as 
a transparent live bridge: [2, 3, 4] 

   1. The Trap: You click a malicious link (often sent via a convincing phishing email). [5, 6] 
   2. The Live Relay: Your browser connects to the attacker’s reverse proxy server. That server immediately connects to the real website (like Microsoft 365, Google, or your bank) on your behalf. [2] 
   3. The Real Interface: The attacker’s server pulls the actual login page from the real website and shows it to you, pixel-for-pixel, in real time. [2] 
   4. Capturing Credentials and Codes: You type your username, password, and even your MFA code or push-notification confirmation. [4] 
   5. Session Hijacking: The proxy passes your inputs to the real website, logs you in, and intercepts the session cookie or authentication token issued to you. The attacker steals that token and logs into your account directly, completely bypassing the need for your password again. [1, 3, 7] 

------------------------------

## Why It Is Dangerous

* Bypasses Traditional MFA: Because you completed a real authentication step, standard SMS codes, app prompts, and basic 2FA do not stop the attacker. [4, 8] 
* Real-Time Execution: The handoff happens in seconds before any security alert triggers. [4] 
* Packaged Kits: Off-the-shelf Phishing-as-a-Service (PhaaS) tools (such as EvilProxy, EvilNginx, or Tycoon 2FA) make this attack easy for low-skill fraudsters to deploy at scale. [4, 9, 10] 

------------------------------

## How to Defend Against It

* Use Phishing-Resistant MFA: Upgrade to FIDO2 / WebAuthn passkeys or hardware security keys (like YubiKeys). These cryptographically bind the login process to the exact website domain, meaning a fake proxy address will fail to authenticate.
* Deploy Browser-Level Protection: Use enterprise security tools or modern browsers that detect look-alike domains and inspect rendered pages in real time.
* Monitor Session Anomalies: IT security teams should track impossible travel, sudden token reuse, or the unauthorized addition of new MFA devices on employee accounts. [4, 9, 11]

# What is OTP relay?

An OTP relay (or an OTP relay attack) is a technique where an attacker intercepts a one-time password and immediately 
forwards it to a legitimate service to break past two-factor authentication. [1, 2] 

## How an OTP Relay Works

   1. The Phishing Setup: The attacker builds a fake website that mimics a real login page (like a bank or email service). [3, 4, 5] 
   2. Credential Capture: The victim visits the fake site and types in their username, static password, and requests an OTP. [2, 4] 
   3. Real-Time Interception: As the victim receives the OTP (via SMS, email, or an authenticator app) and types it into the fake site, the attacker's system catches it in real time. [2, 4] 
   4. Immediate Relay: The attacker rapidly plugs that exact code into the real website before the timer runs out, gaining unauthorized access to the victim's account. [2] 

## Common Delivery Methods and Tools

* Phishing Sites and AitM (Adversary-in-the-Middle): Proxy tools sit between the user and the real website, harvesting cookies and tokens.
* OTP Bots: Automated scripts or Telegram-based tools that help scammers call, text, or trick users into handing over codes.
* SMS Interception: Stealing text messages through SIM swapping, SS7 network exploits, or malicious mobile malware. [4, 5, 6, 7, 8, 9] 

## How to Stop OTP Relay Attacks

* Use Phishing-Resistant MFA: Switch from standard SMS or basic TOTP codes to FIDO2 / WebAuthn passkeys or hardware security keys (like a YubiKey), which cryptographically bind the login to the exact domain name. [6, 8] 
* Use App-Based Authenticators with Context: Modern authenticator apps or push notifications can display sign-in context (such as the location or service name). [6, 8] 
* Train Users to Spot Phishing: Teach users to double-check URL addresses and never share verification codes over the phone or on unverified websites. [1, 7, 10]

# What does TAP-based bootstrap and recovery mean?

TAP-based bootstrap and recovery refers to using a Temporary Access Pass 
(TAP)—primarily in Microsoft Entra ID as a short-lived passcode to onboard 
users to passwordless security or restore access when they lose a device. [1, 2] 

It replaces weak, traditional temporary passwords or phone-read codes with a 
secure, policy-controlled method. [2, 3] 

------------------------------
## Core Concepts## 1. TAP-Based Bootstrap (Onboarding)

* What it means: Setting up a user’s very first strong, passwordless authentication method (such as Windows Hello for Business, a FIDO2 security key, or the Microsoft Authenticator app) without ever using or needing a standard password. [2] 

* How it works: An administrator generates a time-limited TAP in the [Microsoft Entra Admin Center](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-authentication-temporary-access-pass) and hands it to the user. The user signs in with the TAP and immediately registers their permanent passwordless credential. [2, 4] 

## 2. TAP-Based Recovery (Account Restoration)

* What it means: Helping a user regain access to their account when they lose, break, or forget their primary strong authentication factor (like dropping their security key or losing their phone). [2, 5] 

* How it works: Instead of the helpdesk manually resetting a risky password or going through an insecure verification loop, an admin issues a new, single-use TAP. The user logs in with the TAP to re-enroll or fix their primary multi-factor authentication (MFA) method. [2, 5, 6] 

------------------------------
## Key Features of a TAP

* Time-Limited: You can set a TAP to last anywhere from a few minutes up to several days (depending on your organization's policy). [4, 7] 

* Single-Use or Multi-Use: Configured to work for just one login session or multiple times during a brief onboarding window. [4] 

* Satisfies MFA: Entra ID treats a TAP as a strong, MFA-compliant credential, allowing it to satisfy strict Conditional Access policies when registering new security info. [6, 8] 

* Reduces Helpdesk Strain: It eliminates the classic problem of IT reading a temporary password over the phone or sending it unencrypted via email. [2]

# REVIEW-01 ANSWER

Yes—your concerns are well founded. The original description is **conceptually valid**, 
but step 3 and the wording of step 4 are imprecise.

## What actually happens

The attacker does not normally send the Authenticator prompt directly. 

Instead:

1. The attacker starts a genuine Microsoft Entra/Microsoft 365 sign-in.
2. The attacker submits Alice’s valid password.
3. Entra reaches the MFA step, generates a number, displays it in the attacker’s browser, and triggers an Authenticator push notification to the device registered to Alice.
4. Alice’s phone receives the notification—subject to normal notification, network, and device conditions. Alice may need to tap it to open Authenticator.
5. The attacker persuades Alice to enter the number displayed in the attacker’s browser into the Authenticator request.

Microsoft describes number matching as requiring the user to enter the number shown in the sign-in browser 
or application into the Authenticator notification. Thus, the attacker is exploiting a **real authentication request**, not fabricating a Microsoft prompt. 

[Microsoft Learn: How number matching works](https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-mfa-number-match)

The important distinction is:

> The attacker initiates the sign-in that causes Microsoft to send the notification; the attacker does not manually send the notification.

## The call can occur before or after the sign-in request

Both sequences are possible.

### Sequence A: sign-in first, call second

This is close to your original version:

1. The attacker already possesses Alice’s username and password.
2. The attacker starts a real Microsoft 365 sign-in and submits the password.
3. Entra displays a number in the attacker’s browser and triggers an Authenticator notification on Alice’s phone.
4. The attacker calls Alice, impersonating the help desk, and says:  
   “We are testing your account. You should have received a Microsoft Authenticator request. Enter the number I give you.”
5. The attacker reads the number shown in their browser—say, `42`—to Alice.
6. Alice enters `42` into the genuine Authenticator request.
7. Entra completes MFA and may issue the attacker’s browser a session or tokens, subject to applicable Conditional Access and other security controls.
8. The attacker uses the resulting access while claiming that the issue has been resolved.

### Sequence B: call first, sign-in second

This is also plausible and may be more convincing socially:

1. The attacker obtains Alice’s username and password.
2. The attacker calls Alice while impersonating the help desk:  
   “We are going to run a quick sign-in check. I will tell you what number to enter when the Microsoft request appears.”
3. While remaining on the call, the attacker starts the real Microsoft 365 sign-in and submits Alice’s password.
4. Entra generates the number and triggers the Authenticator notification.
5. Alice receives and opens the genuine prompt.
6. The attacker reads the number from their browser, and Alice enters it into Authenticator.
7. The attacker’s sign-in completes.

Calling first allows the attacker to frame the forthcoming notification as expected. But the call alone does not create the prompt; the attacker still has to initiate an authentication attempt that reaches the Authenticator MFA step.

## Suggested corrected version

### The remote help-desk attack

Consider Alice, whose company uses a password plus Microsoft Authenticator number matching:

1. An attacker obtains Alice’s username and password, for example through a previous breach or a phishing site.
2. The attacker starts a genuine Microsoft 365 sign-in from a remote computer and submits Alice’s password.
3. Microsoft Entra validates the password, displays a number such as `42` in the attacker’s browser, and triggers an Authenticator notification on Alice’s phone.
4. The attacker calls Alice, either before or after initiating the sign-in, while impersonating the help desk:  
   “We detected an issue with your account. You should have received a Microsoft Authenticator request. Enter the number I give you into that request.”
5. The attacker reads `42` from their browser, and Alice enters it into the genuine Authenticator request.
6. Entra receives the valid password and successful MFA response and completes the authentication flow for the attacker’s browser.
7. Depending on the organization’s policies and Conditional Access controls, the attacker may receive a usable session or tokens and attempt to access corporate resources.

## One important qualification

Number matching prevents an attacker from succeeding merely by repeatedly sending or triggering blind **Approve** prompts and hoping that the victim taps one accidentally. However, it does **not** by itself prevent a real-time attacker from relaying the displayed number to a victim through a phone call. Microsoft therefore treats number matching as a security improvement, but it is not the same as phishing-resistant authentication such as FIDO2 security keys or passkeys.

So the most accurate summary is:

> The attacker initiates the real login, Microsoft automatically generates and delivers the MFA request, and the attacker uses social engineering to persuade Alice to complete that request on the attacker’s behalf.
