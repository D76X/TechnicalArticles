# Passkeys: From Passwords to Phishing-Resistant Authentication

Passwords have survived for decades because they are easy to understand: a user knows a secret and presents it to a service. That simplicity hides a fundamental architectural weakness. A password is a reusable network secret. Anyone who learns it can present it, from any compatible client, until the password is changed or the account is blocked.

Passkeys replace that shared-secret model with public-key cryptography. The user proves possession of a private key without disclosing it; the service stores only the corresponding public key. The credential is bound to the service for which it was created, and using it requires an explicit local action such as a biometric check or device PIN. The result is an authentication method that is easier for users and substantially more resistant to phishing, replay, credential stuffing, and server-side credential theft.

This article follows the conceptual progression in John Savill's *PASSKEYS - What they are, why we want them and how to use them!* [1], while grounding the explanation in WebAuthn, FIDO, NIST, and current Microsoft Entra documentation. Product behavior changes over time; implementation decisions should always be checked against the current documentation linked in the references.

## 1. Why the password model fails

A password creates the same problem wherever it is used: the verifier and the user must share knowledge of a secret. Even if a service stores only a salted password hash, the user still transmits evidence derived from that password during sign-in, and the password remains valuable to an attacker.

Several familiar attacks follow from this design:

- **Phishing:** a convincing false site asks the user for the secret.
- **Credential stuffing:** a password leaked by one service is tried against other services.
- **Password spraying:** common passwords are tried against many accounts.
- **Replay and adversary-in-the-middle attacks:** an attacker relays a legitimate sign-in and captures credentials or the resulting session.
- **Offline cracking:** stolen password hashes are tested without interacting with the real service.
- **Help-desk abuse:** resets and recovery processes become routes around the password itself.

Password rules do not remove these properties. Longer passwords and password managers improve resistance to guessing and reuse, but the service still accepts a bearer secret.

### What phishing actually is

Phishing is social engineering: an attacker impersonates a trusted person or service and creates a believable reason for the victim to reveal information, open content, approve an action, or sign in. The message is only the delivery mechanism. The attack succeeds when trust, urgency, fear, curiosity, or routine behavior causes the victim to perform an action that benefits the attacker [12][13].

A common credential-phishing sequence is:

1. The attacker chooses an identity to impersonate, such as Microsoft 365, a bank, a courier, an executive, or the internal help desk.
2. The attacker sends a plausible pretext: “Your account will be disabled,” “Review this shared document,” “A payment is waiting,” or “IT detected suspicious activity.”
3. A link or QR code opens a false sign-in page, or a telephone caller asks the victim to read or approve an authentication challenge.
4. The victim enters a password and completes MFA because the page or caller appears legitimate.
5. The attacker reuses or relays that proof, captures the resulting session, and acts as the victim.

The attacker does not need to break cryptography. The objective is to persuade an authorized person to perform the security operation in the wrong context.

### Common phishing variants

The variants differ mainly in targeting and delivery channel:

| Variant | What it looks like | Typical objective |
|---|---|---|
| **Bulk email phishing** | A high-volume fake notice from a bank, cloud provider, or delivery company | Capture credentials or deliver malware |
| **Spear phishing** | A message tailored with the victim's role, colleagues, current project, or supplier | Steal a specific account or obtain an initial foothold |
| **Whaling and business email compromise** | An executive, finance officer, or trusted supplier appears to request an urgent payment or data release | Financial fraud or sensitive-data theft |
| **Smishing** | An SMS or chat message claims that an account, parcel, or payment needs attention | Send the victim to a mobile credential-harvest page |
| **Vishing** | A caller pretends to be the help desk, bank, or authority and asks for a code or approval | Make the victim complete MFA for the attacker's session |
| **Quishing** | A QR code in email, print, signage, or a document moves the destination outside the visible link | Open a phishing site on a phone, often bypassing link inspection |
| **Clone phishing** | A real message is copied and its link or attachment is replaced | Exploit the trust created by a familiar conversation |
| **Consent phishing** | A malicious application asks the user to grant apparently reasonable OAuth permissions | Obtain authorized API access without stealing a password |
| **AiTM or reverse-proxy phishing** | A proxy relays the genuine site in real time while observing both directions | Capture passwords, phishable MFA, and the authenticated session cookie |

SIM swapping is not itself phishing, but phishing and breached personal data can help an attacker persuade a mobile operator to transfer the victim's number. The attacker can then receive SMS codes and password-reset messages. This illustrates why adding SMS to a password is better than a password alone, but is not phishing-resistant authentication.

### A concrete attack against conventional MFA

Consider Alice, who signs in with a password and Authenticator number matching:

1. An attacker already knows Alice's password from a previous breach or phishing page.
2. From a computer in another country, the attacker starts a real Microsoft 365 sign-in as Alice.
3. Entra displays the number `42` in the attacker's browser and sends Alice an Authenticator prompt.
4. The attacker calls Alice, spoofs the help-desk identity, and says: “We detected an attack. To prove you are the account owner, enter 42 in the prompt I just sent.”
5. The prompt really is from Microsoft, and the number matches. Alice follows the instruction.
6. Entra sees the correct password and an approved second factor, so it authenticates the attacker's browser and issues that browser a session.
7. The caller reassures Alice that the incident is resolved while using the new session to access data or establish persistence [12].

Number matching prevented blind “Approve” tapping, but it did not cryptographically connect Alice's phone to the computer being signed in. Alice remained the communication channel between the remote challenge and her authenticator.

Time-based one-time passwords and SMS codes fail similarly: the attacker asks Alice to read the current code and immediately relays it. In an AiTM proxy, no telephone conversation is required. The proxy forwards Alice's password and code to the genuine identity provider and then steals the session cookie returned through the proxy.

### The same attack attempted with a passkey

Assume Alice's organization now requires a passkey and she holds it on her phone.

1. The remote attacker starts a sign-in and asks Alice to “approve” it.
2. There is no transferable code for Alice to read aloud and no number she can type into an unrelated prompt.
3. To use the phone's passkey for the attacker's browser, the WebAuthn cross-device ceremony must be established between that browser and Alice's phone. The devices must participate in the same transaction, and Bluetooth is used in the hybrid flow to verify that the authenticator is physically near the client [1][12][14].
4. The attacker is hundreds of kilometres away, so the attacker's browser cannot satisfy that proximity check with Alice's phone.
5. The private key never leaves the phone, and Alice cannot manually copy a valid signed response to the attacker.

The remote-help-desk attack path therefore stops. The attacker cannot turn Alice into a human relay for the authentication factor.

This statement needs one technical qualification. A passkey used directly on a phone or through a platform authenticator such as Windows Hello does not need a separate Bluetooth proximity check—the authenticator is already on the client device. Proximity is specifically important for roaming and cross-device use. In all cases, the authenticator performs a direct protocol operation for the requesting client rather than giving the user a reusable value to relay.

### How WebAuthn stops a phishing proxy

Physical proximity addresses the remote-client scenario. WebAuthn supplies a second, independent defense against false websites and AiTM proxies: **verifier name binding**, implemented through the web origin and relying-party ID [2][6][15].

Suppose Alice clicks a link to `login-micros0ft.example`, a page that perfectly copies Microsoft branding or proxies the real sign-in page:

1. The browser knows the actual origin that invoked WebAuthn; visual similarity is irrelevant.
2. A script at the attacker's origin cannot request a passkey for `login.microsoft.com`. WebAuthn requires the RP ID to be valid for the calling origin.
3. If the attacker requests a credential for its own domain, Alice has no Microsoft passkey scoped to that RP ID, so the Microsoft credential is not offered.
4. If the request fails, there is no signed assertion for the proxy to relay and no password or OTP for it to capture.
5. A WebAuthn assertion also covers a fresh server challenge and client data, so an old response cannot be replayed for a new sign-in.

The control is inside the browser, operating system, and authenticator. Alice does not have to notice that a letter was replaced with a zero, inspect a certificate, or decide whether the page feels trustworthy. The platform refuses to use the credential outside its registered scope.

This is why passkeys improve on conventional MFA rather than merely making MFA more convenient. Conventional MFA proves that the user supplied two factors; phishing-resistant authentication also binds that proof to the intended verifier and, where an external authenticator is used, to the client physically participating in the ceremony.
### Why traditional MFA is not the final answer

Multifactor authentication reduces risk, but not every MFA method offers the same protection. SMS codes, time-based one-time passwords, and push approvals add a hurdle, yet an attacker can often relay them in real time. Number matching and additional context reduce accidental approval and MFA fatigue, but still ask a person to decide whether a remote request is legitimate.

Microsoft therefore distinguishes **passwordless MFA** from **phishing-resistant MFA**. The built-in phishing-resistant authentication strength includes Windows Hello for Business, passkeys (FIDO2), and certificate-based authentication in supported configurations [8]. Conventional Authenticator push approval is not in that category. Importantly, this statement concerns push approval; a passkey stored by Microsoft Authenticator is a FIDO credential and is evaluated as such.

## 2. The progression from FIDO U2F to passkeys

Early FIDO Universal 2nd Factor (U2F) security keys strengthened password sign-in with a physical authenticator. The user entered a username and password, inserted or tapped a key, and performed a gesture. This was strong but remained a second factor and required users to carry separate hardware.

FIDO2 expanded the model so a public-key credential could be the primary sign-in method. It combines two major specifications:

1. **Web Authentication (WebAuthn):** the W3C browser and web-platform API through which a relying party creates and uses public-key credentials [2].
2. **Client to Authenticator Protocol (CTAP):** the FIDO protocol used when a client communicates with an external authenticator, for example over USB, NFC, or Bluetooth [3].

Modern phones and computers already contain secure hardware and local user-verification mechanisms. The authenticator can therefore be built into the platform instead of always being a separate USB key.

The consumer-facing name **passkey** was introduced to make this passwordless FIDO credential easier to understand. “Passkey” is not a different cryptographic protocol layered on top of FIDO2; it is the user-facing name for a discoverable FIDO credential designed for passwordless sign-in [3][4].

## 3. The components of a passkey system

A clear mental model starts with four roles.

### 3.1 Relying party

The **relying party (RP)** is the website or service that authenticates the user. It has a relying-party identifier, normally an effective domain such as `example.com`. It stores the credential identifier, public key, signature counter or related metadata where applicable, and account association. It does not receive the private key.

### 3.2 Client

The **client** is the operating-system and browser environment that implements WebAuthn [16]. A native application commonly invokes a system browser or platform authentication session rather than implementing the cryptographic ceremony itself.

The client enforces critical security checks. It validates the web origin, checks whether the requested RP ID is valid for that origin, mediates access to authenticators, and returns the authenticator's signed response to the relying party.

### 3.3 Authenticator

The **authenticator** creates and uses the credential. It may be:

- a **platform authenticator**, such as Windows Hello or a phone's native credential provider;
- a **roaming authenticator**, such as a USB/NFC/Bluetooth security key; or
- a credential-provider application, such as a supported password manager or Microsoft Authenticator.

The authenticator protects private-key operations and obtains evidence of user presence or user verification. A biometric template is normally processed locally by the device; it is not sent to the relying party. The relying party receives flags indicating that the required local interaction occurred.

### 3.4 Credential

The passkey is the **credential**, not the phone, app, or security key containing it. Keeping these concepts separate prevents several misunderstandings:

- One authenticator can hold passkeys for many relying parties and accounts.
- One account can have several passkeys on different authenticators.
- A device-bound passkey can remain on one authenticator while that authenticator is used with many client devices.
- A synced passkey can be available through multiple authenticators in the same credential-provider ecosystem.

## 4. Registration: how a passkey is created

Registration is called the WebAuthn **creation ceremony**. A simplified sequence is as follows [2][5]:

1. The user signs in or completes another trusted bootstrap process.
2. The relying party generates a fresh, unpredictable challenge and sends `PublicKeyCredentialCreationOptions` to the client.
3. Those options identify the RP and user, state acceptable algorithms, and express requirements such as user verification, attestation, resident/discoverable credentials, and authenticator preferences.
4. The client calls `navigator.credentials.create()` and validates that the RP ID is permitted for the current origin.
5. The user chooses an authenticator and performs its required local gesture.
6. The authenticator creates a new asymmetric key pair scoped to that RP. The private key remains protected by the authenticator or its synchronization system.
7. The authenticator returns the public key and signed registration data. Depending on policy, it can also return attestation information describing the authenticator.
8. The relying party validates the challenge, origin, RP ID hash, signature, flags, and requested properties, then associates the public key and credential ID with the user's account.

The challenge is essential. Because it is fresh and single-use, a captured registration response cannot simply be replayed later.

Registration must itself be protected. If an attacker can add their passkey to a victim's account, the strength of later passkey sign-ins does not help. Enterprises should require a strong existing method or controlled bootstrap credential. Microsoft Entra supports a **Temporary Access Pass (TAP)** for onboarding and recovery of passwordless methods [9].

## 5. Authentication: how a passkey proves identity

Authentication is the WebAuthn **assertion ceremony**:

1. The user opens the genuine relying party.
2. The relying party creates a new random challenge and sends `PublicKeyCredentialRequestOptions`.
3. The client calls `navigator.credentials.get()`.
4. The client and authenticator identify credentials valid for the requested RP. A discoverable credential can allow account selection without first typing a username.
5. The user approves the operation and, when required, verifies locally with a biometric or PIN.
6. The authenticator signs data that includes the challenge and RP-specific authenticator data with the private key.
7. The client returns the assertion, client data, and credential identifier to the relying party.
8. The relying party retrieves the public key and verifies the signature, challenge, origin, RP ID hash, and user-presence or user-verification flags.
9. If validation succeeds, the service creates its normal authenticated session or tokens.

A signature is **verified**, not decrypted. The public key proves that the holder of the matching private key produced the assertion, but it cannot be used to derive that private key.

## 6. Why passkeys resist phishing

Passkeys derive phishing resistance from **verifier name binding**. NIST defines this as cryptographically binding authenticator output to an authenticated verifier name [6]. In WebAuthn, the RP ID and web origin provide that binding.

Suppose a user is sent to `micr0soft.example` while believing it is a Microsoft sign-in page. The malicious origin cannot request a credential scoped to `microsoft.com`; the client rejects an RP ID that is not valid for the calling origin. If the false site asks for its own RP ID, no Microsoft credential is available. The decision is made by the platform, not by the user's ability to spot a substituted character.

This also defeats the usual real-time phishing proxy. A one-time code can be copied from one browser session into another. A WebAuthn assertion contains a fresh challenge and is bound to the legitimate RP. An assertion generated for the attacker's origin is invalid at the real site, while the attacker's origin cannot request the real site's credential.

### Presence, verification, and intent

Three related properties should not be conflated:

- **User presence (UP)** means a person interacted with the authenticator, for example by touching a key.
- **User verification (UV)** means the authenticator locally verified the person through a PIN, biometric, or equivalent mechanism.
- **Explicit intent** comes from the mediated ceremony: the user selects or approves use of a credential for the current request.

When user verification is required, a passkey can satisfy multiple factors in one ceremony: possession of the authenticator plus knowledge of its local secret or an inherence factor. The biometric itself is not an Internet credential.

### The role of proximity

Proximity is particularly relevant to **cross-device authentication** and roaming authenticators. USB and NFC inherently require a nearby authenticator. In the hybrid cross-device flow, a QR code establishes the transaction and Bluetooth helps demonstrate that the phone is near the client; encrypted communication can then continue through an Internet-assisted tunnel [3].

Proximity is a valuable defense against a remote attacker tricking a user into approving the attacker's computer. It is not, however, the sole basis of WebAuthn phishing resistance. Origin/RP binding remains the decisive protection against a credential being used at the wrong website. A platform authenticator already resides on the client device and requires no separate CTAP proximity proof.

## 7. Discoverable credentials and usernameless sign-in

A passkey is normally a **discoverable credential**. The authenticator can find credentials associated with the requested RP without the server first providing a list tied to a username. This enables conditional UI and usernameless flows: the platform presents eligible accounts, the user selects one, and the signed assertion identifies the credential to the relying party.

Discoverability improves usability but does not make one credential reusable across websites. Each credential remains scoped to an RP and account. The authenticator may display several accounts for the same RP, but it should not offer credentials for unrelated domains.

## 8. Device-bound and synced passkeys

The storage and lifecycle model creates two broad passkey categories [17].

### 8.1 Device-bound passkeys

A device-bound passkey is designed so its private key cannot be exported from its authenticator. Examples include many hardware security keys and enterprise credentials protected by device hardware.

Advantages include strong knowledge of where the key resides, easier alignment with some regulatory controls, and reduced dependence on a cloud synchronization account. The operational cost is recovery: loss or replacement of the authenticator requires another registered method, a spare security key, or a controlled bootstrap such as TAP.

### 8.2 Synced passkeys

A synced passkey is end-to-end protected and synchronized by a credential provider across a user's trusted devices. This makes device replacement and everyday use easier. Users do not need to register a new credential separately on every device in the ecosystem.

Synchronization changes the trust boundary. The organization must assess the credential provider's account recovery, device enrollment, encryption, enterprise management, and revocation properties. Synced does not mean “public” or “stored unencrypted in the cloud,” but it does mean assurance depends partly on the provider's ecosystem and controls.

The distinction applies to the credential, not to whether an authenticator can be carried around. A phone holding a device-bound passkey can still authenticate the user on several computers through cross-device authentication; the key has not moved, even though the authenticator roams.

## 9. Same-device and cross-device experiences

### Same-device authentication

When the passkey is available to the device on which sign-in occurs, the sequence is intentionally short:

1. Open the service.
2. Select the offered passkey or account.
3. Complete local user verification.
4. Continue into the authenticated session.

The platform can offer the credential because its RP scope matches the site. Subsequent visits become simpler without weakening the cryptographic ceremony.

### Cross-device authentication

A typical phone-to-PC flow is:

1. Choose to use a passkey from another device.
2. The PC displays a transaction-specific QR code.
3. Scan it with the phone that holds the passkey.
4. The devices establish the hybrid flow and check proximity, commonly using Bluetooth.
5. Select the appropriate RP-bound passkey on the phone.
6. Complete local user verification on the phone.
7. The signed assertion returns to the browser session on the PC.

The private key never has to be copied to the PC. This is different from synchronization: cross-device authentication uses a nearby authenticator for one ceremony, whereas synchronization makes a credential available through multiple authenticators managed by one provider.

## 10. Passkeys in Microsoft Entra ID

Microsoft Entra exposes passkeys through the **Passkey (FIDO2)** authentication-method policy [5][10]. A sound enterprise configuration separates three decisions.

### 10.1 Who may register and use passkeys?

Target the authentication-method policy to pilot groups before broad deployment. Keep break-glass and service-account requirements separate from the normal workforce design.

### 10.2 Which authenticators are acceptable?

Entra passkey profiles can express requirements for device-bound or synced passkeys, attestation, and authenticator restrictions. Authenticator models are identified through an **Authenticator Attestation GUID (AAGUID)**. Allowing or blocking AAGUIDs lets an organization restrict enrollment to evaluated authenticators or react to a product vulnerability.

Attestation and AAGUID restrictions solve different problems. An AAGUID states an authenticator model identifier in registration data; attestation provides cryptographic evidence about the authenticator and registration. Neither should be enabled reflexively. Restrictions reduce user choice and can complicate registration campaigns, so they need an assurance-driven reason and lifecycle process.

### 10.3 What access requires a phishing-resistant method?

Enabling registration does not ensure that applications require passkeys. Conditional Access authentication strengths can require **phishing-resistant MFA** for selected users, applications, actions, or risk conditions [8]. Device compliance, sign-in risk, location, and session controls remain separate policy dimensions. A strong credential does not make an unmanaged or compromised endpoint healthy.

### Registration and recovery

Users can register at `https://mysignins.microsoft.com/security-info` when self-service setup is allowed. For first-time onboarding or replacement of a lost device, TAP provides a time-limited bootstrap path [9]. Administrators should design recovery before enforcing passwordless sign-in:

- require more than one usable authentication method where practical;
- define lost-device reporting and credential deletion procedures;
- issue TAP only after adequate identity verification;
- monitor authentication-method registration and deletion;
- revoke sessions when compromise is suspected.

Microsoft Authenticator has platform- and version-specific passkey requirements, and its support for device-bound or synced behavior can evolve. The current support matrix and published AAGUIDs should be taken from Microsoft Learn rather than copied permanently into internal instructions [7].

## 11. Microsoft accounts and consumer passkeys

Personal Microsoft accounts also support passkey sign-in [11]. The underlying ceremony is the same: the service stores a public key, the authenticator protects the private key, and WebAuthn binds the response to Microsoft's RP. Available credential providers and synchronization options depend on the operating system, browser, and provider.

This consistency is a major advantage of an open standard. Users can learn one high-level interaction—choose a passkey and unlock it locally—across Microsoft, Google, Apple, and other relying parties, even though each service manages its own account and public key.

## 12. What passkeys solve—and what they do not

Passkeys substantially reduce:

- password phishing and credential stuffing;
- reuse of a credential across relying parties;
- replay of captured authentication assertions;
- theft of reusable secrets from a relying-party credential database;
- remote approval attacks in properly implemented cross-device flows;
- user dependence on memorized secrets [13][14].

They do not eliminate:

- malware that controls an already authenticated endpoint;
- theft of active session cookies or tokens after authentication;
- malicious OAuth consent and other authorization attacks;
- insecure account recovery or help-desk processes;
- an attacker enrolling their authenticator after account takeover;
- compromise of the credential provider or synchronization account;
- application defects and data breaches unrelated to credentials.

A database of public keys is not useful for impersonating users, but a compromised server can still expose personal data, alter application behavior, or steal sessions. Passkeys improve the authentication boundary; they do not replace endpoint security, secure software design, Conditional Access, monitoring, or incident response.

## 13. Practical architecture guidance

A passkey program should be treated as an identity architecture change rather than a portal toggle.

1. **Define assurance tiers.** Decide which populations can use synced credentials and which require device-bound, attested authenticators.
2. **Inventory clients.** Validate operating systems, browsers, mobile-device management, Bluetooth policy, VDI, shared workstations, and accessibility needs.
3. **Design bootstrap and recovery.** Establish identity proofing, TAP issuance, spare authenticators, loss handling, and revocation.
4. **Pilot representative journeys.** Test same-device, cross-device, device replacement, multiple accounts, and restricted authenticator profiles.
5. **Enable registration deliberately.** Use targeted groups and a communication campaign before enforcing an authentication strength.
6. **Apply Conditional Access.** Require phishing-resistant MFA where the business risk justifies it, while preserving emergency access.
7. **Measure outcomes.** Track registration coverage, method usage, failures, recovery calls, and sign-in risk rather than counting only enrolled credentials.
8. **Retire weaker paths carefully.** A passwordless front door is undermined if easy recovery or legacy authentication still accepts weak proof.

## Conclusion

The important change introduced by passkeys is not merely that a biometric replaces typing. The architecture changes from presenting a reusable secret to proving possession of an RP-bound private key. WebAuthn checks the origin, the authenticator requires local participation, and the relying party validates a signature over a fresh challenge using a public key that is safe to store.

FIDO2 makes strong cryptography available through a simple ceremony. CTAP and hybrid transport extend that ceremony to nearby authenticators; discoverable credentials remove unnecessary username entry; synchronization can make recovery and multi-device use practical. Microsoft Entra then adds enterprise controls around eligible users, authenticators, bootstrap, and Conditional Access.

Passkeys should therefore be understood as both a user-experience improvement and a security architecture improvement. Their strongest benefit appears when organizations also protect enrollment, recovery, endpoints, and sessions—and when weaker fallback methods are reduced rather than left as permanent bypasses.
