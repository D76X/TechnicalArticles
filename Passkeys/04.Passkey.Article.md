# Passkeys: The Phishing-Resistant Successor to Passwords and Conventional MFA

Passwords are convenient for computers but difficult for people. We are expected to create a different, long secret for every service, 
remember or safely store it, recognize false sign-in pages, and never reveal the secret to somebody who sounds trustworthy. 
When any part of that human process fails, the password can be used from anywhere in the world [1].

Multifactor authentication (MFA) made this situation substantially safer. A stolen password is less useful if the attacker also needs a code, 
phone, or approval. However, many familiar MFA methods remain **phishable**: a user can still be persuaded to read a code, enter a number, or 
sign in through a malicious proxy. MFA proves that multiple factors were supplied; it does not necessarily prove that they were supplied to 
the intended website from the intended client.

Passkeys change that architecture. They replace the reusable network secret with public-key cryptography, bind each credential to the site 
for which it was created, and require the authenticator to participate directly in the sign-in. When the authenticator is external to the 
client, its physical presence is established through USB, NFC, or a Bluetooth-assisted cross-device flow. The user has no password or one-time 
value that can be handed to a remote attacker.

This article explains the following: 

- the problem passkeys solve, 
- how `WebAuthn` and `FIDO2` work, 
- why conventional MFA can still be phished, 
- how the same attacks fail against passkeys, and 
- how Microsoft Entra ID can deploy and recover them safely

## What phishing is: an attack on the human protocol

Phishing is a form of social engineering. The attacker impersonates a trusted organization or person 
and creates a plausible reason for the victim to act. The message might say that an account will be suspended, 
a shared document is waiting, a payment failed, a parcel cannot be delivered, or the help desk detected an emergency [8].

The attacker is not usually trying to break the cryptography behind TLS or MFA. The objective is to convince an authorized 
user to perform a legitimate security action in the wrong context.

A typical credential-phishing attack has five stages:

1. **Impersonation.** The attacker copies a brand, display name, writing style, login page, or telephone identity.
2. **Pressure.** Urgency, fear, authority, curiosity, or routine creates a reason to act before verifying the request.
3. **Redirection.** A link, attachment, QR code, text message, or caller moves the victim into an attacker-controlled interaction.
4. **Credential capture or relay.** The victim enters a password, reveals a code, approves a prompt, grants application consent, or installs remote-control software.
5. **Account use.** The attacker receives credentials or a session, accesses data, changes recovery methods, and attempts lateral movement.

### Common variants

Phishing is broader than a badly written email:

| Variant | Delivery and targeting | Example |
|---|---|---|
| Bulk phishing | High-volume email or messaging | A fake Microsoft 365 expiration notice |
| Spear phishing | Personalized for one person or team | A project document apparently sent by a colleague |
| Whaling | Targets executives or other high-value users | A confidential legal or acquisition request |
| Business email compromise | Impersonates an executive or supplier | An urgent change to bank-payment details |
| Smishing | SMS or chat | A parcel or bank alert linking to a mobile login page |
| Vishing | Telephone or voice message | “IT support” asks the user to read or approve an MFA challenge |
| Quishing | QR code | A printed or emailed code opens a false sign-in page on a phone |
| Clone phishing | Copies a genuine message but replaces content | A familiar invoice with a malicious link or attachment |
| Consent phishing | Requests OAuth authorization for a malicious app | A “document viewer” asks to read mail and files |
| AiTM proxy phishing | Relays a real service through an attacker-controlled domain | A Microsoft 365 proxy captures the password, OTP, and resulting cookie |

Malicious attachments and remote-support tools are another branch: instead of stealing the credential, the attacker tries to control the legitimate endpoint or steal an existing session. Passkeys do not make these attacks disappear, which is why endpoint protection and user education remain necessary.

SIM swapping is related but distinct. By impersonating the victim to a mobile provider, an attacker transfers the phone number to a SIM they control and receives SMS authentication and recovery messages. This is one reason SMS is stronger than a password alone but weaker than phishing-resistant authentication.

## Why consolidated MFA can still be phished

MFA combines factors from categories such as:

- something the user **knows**, such as a password or PIN;
- something the user **has**, such as a phone, smart card, or security key;
- something the user **is**, such as a fingerprint or facial characteristic.

The improvement is real. An attacker who steals only the password might still be blocked. The weakness is that many implementations convert the second factor into information or an approval that a person can relay.

### The remote help-desk attack

Consider Alice, whose company uses a password plus Authenticator number matching:

1. An attacker obtains Alice's password from an earlier breach or false login page.
2. The attacker starts a real Microsoft 365 sign-in from a remote computer.
3. Microsoft displays `42` in the attacker's browser and sends a number-matching prompt to Alice's phone.
4. The attacker calls Alice while impersonating the help desk: “We detected an attack on your account. To prove that you are Alice, enter 42 in the prompt I just sent.”
5. The prompt is genuinely from Microsoft and the number is correct, so Alice complies.
6. Microsoft receives a valid password and second factor and issues a session to the **attacker's browser**.
7. The caller says the incident is resolved while using that session to access corporate resources [2].

Number matching has prevented blind approvals and reduced MFA fatigue, but it has not cryptographically connected Alice's phone to the client being authenticated. Alice is the communication bridge between two devices that might be thousands of kilometres apart.

SMS and time-based one-time passwords have the same relay property. A caller or false page asks for the current code and uses it immediately. The code can expire after 30 seconds and still provide enough time.

### The phishing-proxy attack

An adversary-in-the-middle (AiTM) toolkit automates the relay:

1. Alice follows a link to an attacker-controlled domain that resembles her normal identity-provider page.
2. The proxy fetches and displays content from the real identity provider.
3. Alice's username and password pass through the proxy to the genuine service.
4. The genuine service asks for MFA. The proxy relays that prompt or form to Alice.
5. Alice completes SMS, TOTP, or push-based MFA normally.
6. The genuine service returns an authenticated session cookie through the proxy.
7. The proxy copies the cookie, and the attacker reuses it to enter the service as Alice.

The user might see a convincing page and complete a real authentication. The problem is that the proof is not cryptographically bound to the browser origin Alice intended to trust.

## What a passkey is

A passkey is a discoverable FIDO credential based on public-key cryptography. 

It consists logically of:

- a **private key**, protected by the user's authenticator or credential-provider ecosystem;
- a **public key**, stored by the relying party, such as Microsoft, a bank, or an online shop;
- metadata that associates the credential with the relying party and user account.

The private key is not sent to the website. During authentication, it signs data containing 
a fresh challenge. The service verifies that signature with the public key.

This is fundamentally different from a password. 
A password is a bearer secret: whoever knows it can present it. 

A private key is used to produce a signature but is not disclosed. Stealing the service's public-key 
database does not provide what is needed to impersonate its users.

“Passkey” is the user-facing name for this passwordless FIDO credential. The technical foundation 
combines two specifications [3][4]:

- **WebAuthn**, the W3C web API and security model used by the browser and relying party;
- **CTAP**, the FIDO client-to-authenticator protocol used for external authenticators and cross-device communication.

## The four participants

### Relying party

The **relying party (RP)** is the website or service performing authentication. It sends challenges, stores public keys, 
validates signed assertions, and creates the application session. Its RP ID is normally an effective domain such as 
`example.com`.

### Client

The **client** is the browser and operating-system environment. It calls the WebAuthn API, validates the 
requesting origin and RP ID, communicates with an authenticator, and returns the result to the relying party.

For a web application, the important calls are conceptually:

- `navigator.credentials.create()` to register a credential;
- `navigator.credentials.get()` to authenticate with one [3][7].

### Authenticator

The **authenticator** creates and uses the key. 

It can be:

- a platform authenticator, such as Windows Hello or a phone's built-in credential provider;
- a roaming USB, NFC, or Bluetooth security key;
- a supported credential-provider application or password manager.

The authenticator obtains user presence and, where required, local user verification through a PIN or biometric. 
The biometric template stays on the device. The relying party receives evidence that verification occurred, not 
the user's fingerprint or facial image.

### Passkey credential

The passkey is the credential, not the phone or application containing it. One authenticator can hold credentials 
for many sites. One account can have several passkeys. A phone containing a device-bound passkey can be used with 
several nearby computers without copying its private key to them.

### Where the keys live

The most important storage rule is simple: the relying party stores the **public key**, not the password and not 
the private key. It also stores a credential ID and account metadata so it knows which public key to use. 
The private key is held by the authenticator that created the credential [20][21]. During a sign-in, the service sends 
a fresh challenge, the authenticator signs it locally, and the relying party verifies the signature with the public key.

This changes the consequences of a relying-party database breach. A stolen password database contains reusable bearer 
secrets: an attacker can try those passwords against the service or other services where users reused them. A stolen 
passkey database contains public verification material. Possessing a public key does not allow an attacker to create 
a valid signature, derive the private key, or authenticate as the user. In cryptographic terms, disclosure of the public 
key does not defeat the proof-of-possession requirement.

That does not make every database field harmless. A breach can still expose account identifiers, personal data, 
credential metadata, or the ability to tamper with records if the attacker obtains write access. Passkeys specifically 
remove the reusable authentication secret from the relying party; they do not protect unrelated application data or 
an already-issued session.

If an authenticator is lost, suspected compromised, or no longer trusted, the old public key is not recovered or 
mathematically regenerated. The user completes a trusted recovery or reauthentication process, registers a **new credential**, 
and thereby creates a new key pair and public key. The service can then disable or remove the old credential, revoke relevant sessions, and retain the replacement public key. This is credential rotation, analogous to replacing a lost security key, rather than 
resetting a password stored by the service.

### Device-bound and synced private keys

For a **device-bound** passkey, the private key never leaves the authenticator. It may be protected by 
a hardware security key, a device TPM, or another platform authenticator. A phone can authenticate to a 
nearby computer using an approved cross-device flow, but the private key remains on the phone; proximity 
transports the authorization result, not a copy of the key.

A **synced** passkey has a different custody model. The credential provider or platform ecosystem—such as 
Apple, Google/Android, Microsoft, or a supported password manager—protects the credential and synchronizes 
it so that trusted devices associated with the same ecosystem account can use it. The relying party still 
receives only the public key, never the private key. However, the provider's account security, device protection, 
synchronization service, recovery process, and policies become part of the trust boundary. Synced does not mean 
public or unprotected; it means that the provider deliberately makes the protected credential available on more 
than one authenticator.

In both models, the user does not need to remember a password or type a network secret. The normal action is 
a local user gesture: a biometric check or a PIN for the authenticator. The PIN is local to that authenticator 
and is not sent to the relying party, and the relying party receives proof that verification occurred rather 
than the biometric template. Users still need a safe recovery plan, because losing every trusted authenticator 
can prevent access even though there is no password to reset [20].

## How registration works

Registration is the WebAuthn **creation ceremony**:

1. The user first establishes a trusted session, for example with existing MFA or a Temporary Access Pass (TAP).
2. The relying party creates a fresh random challenge and sends credential-creation options.
3. The browser verifies that the requested RP ID is valid for the current secure web origin.
4. The user chooses an available authenticator and confirms the operation.
5. The authenticator creates a new asymmetric key pair for that relying party.
6. The authenticator protects the private key and returns the public key, credential ID, and signed registration data.
7. The relying party checks the challenge, origin, RP ID hash, signature, user-verification flags, algorithms, and any required attestation.
8. The relying party associates the public key with the user's account.

Every service receives a different credential. There is no universal passkey value equivalent to reusing one password across several websites.

Registration is a high-risk operation. If an attacker can register the attacker's authenticator on Alice's account, 
strong future sign-ins will faithfully authenticate the attacker. Enrollment, recovery, and authentication-method changes 
therefore need controls as strong as normal sign-in; to this end the Microsoft Verified ID technologies may be employed.

## How authentication works

Authentication is the WebAuthn **assertion ceremony**:

1. The relying party sends a new random challenge and its RP ID.
2. The client asks available authenticators for credentials matching that RP ID.
3. A discoverable credential lets the platform show eligible accounts without first requiring a username.
4. The user selects the passkey and completes local verification with a PIN or biometric.
5. The authenticator signs the challenge and RP-specific authenticator data with the private key.
6. The relying party finds the stored public key and verifies the signature, challenge, origin, RP ID hash, and required flags.
7. The service creates its normal authenticated session.

The public key verifies a signature; it does not decrypt the private-key operation. 
The one-time challenge prevents a captured assertion from being replayed in a later ceremony.

## The two phishing-resistant properties

Passkeys stop the earlier attacks through two complementary controls. They should be explained 
separately because each addresses a different deception.

### 1. The authenticator must participate with the client

With an external authenticator, the authenticator must be physically associated with the client performing sign-in:

- a USB key is inserted into that client;
- an NFC key is held near it;
- a phone-to-computer flow uses a transaction-specific QR code and Bluetooth to establish nearby presence before protected communication continues;
- a platform authenticator such as Windows Hello is already inside the client.

This removes the transferable code and the human relay. Alice cannot read a cryptographic response 
from her passkey to a caller. The private key performs the operation only within the mediated ceremony.

In the earlier help-desk attack, Alice's phone is not near the attacker's remote computer. 
The attacker cannot establish the cross-device Bluetooth proximity required to use her phone's passkey 
for that client. The social-engineering script no longer produces a valid sign-in.

The phrase “passkeys require proximity” therefore needs precision. A separate proximity check is relevant 
to roaming and cross-device authenticators. A same-device platform authenticator is already physically part 
of the client. In both cases, the authenticator communicates directly with the participating client instead 
of issuing a value the user can relay.

### 2. WebAuthn binds the credential to the genuine site

NIST calls this property **verifier name binding** [5]. 
WebAuthn implements it with the web origin and RP ID.

Assume Alice opens `login-micros0ft.example`, which looks exactly like Microsoft or operates as a reverse proxy:

1. The browser knows that the calling origin is the attacker's domain.
2. Code from that origin cannot request a passkey scoped to `login.microsoft.com`; the RP ID is not valid for the calling origin.
3. If the attacker requests its own RP ID, Alice's Microsoft credential is not eligible and is not presented.
4. If the attacker relays a genuine Microsoft challenge, the client data still records the attacker's origin, so Microsoft rejects the response.
5. The attacker receives no password, OTP, or valid assertion to replay.

The user does not have to detect the substituted character or understand certificates. The WebAuthn client 
enforces credential scope even when the false page is visually perfect.

This is the decisive improvement over phishable MFA: authentication is bound not only to factors, but also 
to the intended verifier and the client participating in the ceremony.

## Lifecycle trade-offs: device-bound and synced passkeys

The key-storage model above also determines the credential's lifecycle and the trust an organization places in the platform.

### Device-bound passkeys

A device-bound private key is designed not to leave its authenticator. Hardware security keys, some platform credentials, and supported authenticator-app credentials use this model. The organization can have higher confidence about where the key resides and can require attestation from approved authenticator models, which suits privileged or regulated accounts. 

The cost is operational: losing the authenticator requires another registered credential or a controlled recovery path.

### Synced passkeys

A synced passkey is end-to-end protected and synchronized through a credential-provider ecosystem, such as iCloud Keychain or Google Password Manager. A passkey created on an iPhone can become available on the user's other trusted Apple devices; a Google Password Manager credential can appear in supported Android and Chrome experiences [9][10]. Synchronization improves usability and device replacement, but it extends the trust boundary to the provider's device enrollment, account security, encryption, and recovery. Synced passkeys are still RP-bound and phishing-resistant, but organizations should decide where that provider trust is acceptable.

Synchronization is not the same as cross-device authentication:

- **Synchronization** makes one credential available through several trusted devices in a provider ecosystem.
- **Cross-device authentication** uses a nearby device for one sign-in without copying its key to the client.

## Passkeys in Microsoft Entra ID

Microsoft Entra separates permission, credential assurance, adoption, and enforcement [19].

### Authentication-method policy and profiles

The **Passkey (FIDO2)** authentication-method policy determines which users can register and use passkeys. 

Passkey profiles then determine which credential types are accepted [6]. 

Profiles can control:

- device-bound and synced passkeys;
- authenticator attestation;
- allowed or blocked Authenticator Attestation GUIDs (AAGUIDs), which identify authenticator models or providers;
- the users and groups receiving each profile.

A practical design might allow device-bound and synced credentials for normal employees while assigning privileged administrators a device-bound, attested, AAGUID-restricted profile. Enforced attestation and synced passkeys are not combined in the current profile model, so assurance and convenience must be balanced deliberately [9][10].

If a user receives multiple profiles, the effective allowed choices must be tested. 

Conditional Access remains separate: even when a synced credential is accepted, policy can still require a compliant, managed, low-risk endpoint.

### Registration campaigns

Enabling the method does not make users enroll. A Microsoft Entra registration campaign can prompt in-scope users after they complete ordinary sign-in and MFA [11]:

1. The user completes MFA.
2. Entra evaluates campaign scope and whether an applicable local passkey is available for the current device/browser combination.
3. The user is prompted to register, or can snooze according to policy.
4. With limited snoozes enabled, registration becomes required after three postponements.

A campaign can target either passkeys or Microsoft Authenticator, not both simultaneously in one tenant. Explicitly enabled campaigns provide administrator control over the method, targeting, and snooze behavior. Microsoft-managed mode applies service-selected defaults and can evolve as Microsoft rolls out recommended settings.

The nudge is contextual, not simply account-wide. A user with Windows Hello on a Windows computer might not be prompted there but can be prompted on a Mac where that credential is unavailable. This is expected behavior.

Campaign scope must match passkey profiles. If a device-bound-only user is nudged and chooses a synced provider, the profile correctly rejects registration but the user sees a confusing failure. Pilot groups and precise instructions are therefore essential.

### Automatic profile rollout

Microsoft introduced automatic passkey-profile rollout to preserve earlier FIDO2 policy intent while adding the new profile and synced-passkey model [12]. Existing targeting and AAGUID restrictions feed the generated default profile. An attestation-enabled policy remains device-bound; a policy without attestation can permit device-bound and synced credentials.

Administrators should inspect the effective result rather than assume migration created the desired model. Microsoft-managed campaign settings can change independently, while a disabled campaign remains disabled.

### Conditional Access enforcement

Registration is not enforcement. Conditional Access authentication strengths can require **phishing-resistant MFA** for selected users, applications, actions, and risk levels [13]. 

Microsoft includes the following authentication in the **phishing-resistant MFA** strength.

- passkeys, 
- Windows Hello for Business, and 
- supported certificate-based authentication .

Rollout should therefore follow this order:

1. define acceptable authenticators and recovery assurance;
2. enable passkey profiles for pilot users;
3. register and test passkeys;
4. expand the campaign by compatible user groups;
5. require phishing-resistant MFA for high-value resources;
6. reduce weaker fallback methods when recovery is ready.

## Recovery must not reintroduce phishing

Passkeys protect sign-in, but account recovery can become the weakest link. If a caller can persuade the help desk to remove the passkey and issue an easy replacement, the attacker has bypassed the cryptography through process.

At minimum, organizations should prepare TAP-based bootstrap and recovery before enforcement [18]:

- register a second independent authenticator for sensitive accounts;
- define lost-device reporting and session-revocation procedures;
- issue TAP only after strong identity verification;
- restrict TAP lifetime and usage;
- monitor authentication-method registration and deletion;
- maintain protected emergency-access accounts.

### Verified ID, Face Check, and TAP

Microsoft demonstrates a higher-assurance passwordless recovery pattern using Microsoft Entra Verified ID [10][14]:

1. A user who lost the passkey device selects **Recover your account**.
2. A trusted identity-proofing service checks a government-issued document and a live selfie.
3. The user obtains or presents a verifiable credential containing trusted identity evidence.
4. Verified ID Face Check compares a live capture with the trusted photo claim. The verifier receives a match result rather than the underlying biometric image [15].
5. After policy accepts the proof, the service issues a short-lived Temporary Access Pass.
6. The user signs in with TAP and registers a new passkey on the replacement device.
7. The organization removes obsolete credentials and revokes suspicious sessions.

Each element has a separate role. The verifiable credential carries signed claims from a trusted issuer. Face Check provides liveness and facial matching between the current person and the credential's photo. TAP gives limited bootstrap access to register a new authentication method. TAP does not prove identity by itself; secure issuance depends on the preceding verification.

This pattern is especially relevant for privileged or sensitive accounts because it removes knowledge-based questions and reduces reliance on a help-desk agent's judgement. It is configurable and availability- and licensing-dependent, not automatically enabled with passkeys.

For a deeper treatment of the issuer-holder-verifier model, verifiable presentations, decentralized identifiers, trust systems, and Face Check, see the author's earlier articles, [*Decentralized Identity Systems Concepts*][16] and [*Decentralized Identity Systems: Under the Hood*][17].

## What passkeys do not solve

Passkeys substantially reduce password theft, credential stuffing, OTP relay, remote approval fraud, and reverse-proxy credential phishing. They do not solve every identity attack.

An attacker can still:

- trick a user into installing remote-control software;
- operate an already unlocked or compromised endpoint;
- steal an active session through malware or a browser vulnerability;
- obtain dangerous OAuth consent;
- exploit an insecure enrollment or recovery process;
- abuse application authorization flaws;
- compromise data stored by the service;
- attack the synchronization provider or its account-recovery process.

Passkeys strengthen authentication. They do not replace endpoint security, application security, Conditional Access, token protection, least privilege, monitoring, or incident response.

## A practical deployment checklist

A passkey project is an identity architecture change, not a portal toggle.

1. **Establish the baseline.** Measure current authentication methods, phishable MFA usage, target platforms, and recovery calls.
2. **Define assurance tiers.** Decide which users can use synced credentials and which require device-bound, attested authenticators.
3. **Design recovery first.** Test spare authenticators, TAP issuance, identity proofing, Verified ID where appropriate, and session revocation.
4. **Inventory user journeys.** Include Windows, macOS, iOS, Android, browsers, VDI, shared workstations, accessibility requirements, and cross-device sign-in.
5. **Pilot profiles.** Verify allowed and deliberately blocked authenticators for every target group.
6. **Communicate the choice.** Explain which provider or key users should select and that biometric data remains local during passkey sign-in.
7. **Run a targeted campaign.** Start with unlimited postponement, monitor failures, then tighten snooze behavior after the path is stable.
8. **Enforce gradually.** Apply phishing-resistant authentication strengths to privileged and high-value access before broader expansion.
9. **Remove bypasses.** Retire weak methods and recovery paths in controlled stages.
10. **Measure actual use.** Registration count is not enough; track successful passkey sign-ins, failures, fallback use, and recovery outcomes.

## Conclusion

Passwords and many MFA methods depend on a person correctly handling transferable proof. Phishing exploits that dependency. A caller can ask for a code, a false page can relay it, and a reverse proxy can capture the resulting session.

Passkeys remove the reusable secret and move authentication into a cryptographic ceremony. The authenticator signs a fresh challenge; the relying party verifies it with a public key. A remote caller cannot ask the user to read out the private-key result. In cross-device flows, the authenticator must be physically near the client. WebAuthn independently checks the real origin and RP ID, so a lookalike domain or phishing proxy cannot invoke the credential for the genuine service.

That is why passkeys are more than passwordless convenience. They build phishing resistance into the protocol instead of relying on the user's ability to recognize every deception. Combined with careful passkey profiles, registration campaigns, Conditional Access, and high-assurance recovery, they provide a practical path beyond passwords and phishable MFA.
